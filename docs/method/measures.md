# Measures and their types

Part of the method (`docs/methodology.md` is the index). Measured results and trials: `docs/method/history.md`.

**Versions.** Every file in `analysis/labels/` carries a `version` column: `v1.0` from 2026-10-22, a wording revision raises the minor number of the rows it changes (v1.1, v1.2), and the major number changes only when the decision model that grades the sentences changes. The column is for people: runs and stored answers are keyed on the exact questions, never on it.

## 5c. A measure through the funnel (`src/measure.py`, `./wbg measure <set>`)

Each measure is one label set in `analysis/labels/`: a definition that names the intervention and never the asset (the model reads literally: a tower-siting sentence scored 0.17 for "a climate risk assessment of its digital infrastructure" and 0.97 for "a climate risk assessment"), a `boundary` line the pair checks read, a scale, search phrases, optional word patterns and a type list. Every number below is a control-panel setting.

1. **The pool.** The units a measure's word patterns match (lead-in included), plus every unit whose best cosine over the measure's phrases and definition reaches the gate: the skip rule's fitted gate, else `measure.gate_cosine` (section 5g); `measure.top` adds the best N by cosine (off by default). No model reads anything here.
2. **The decision model** reads each unit once: the measure's graded question about the sentence alone, its list lead-in in front, with section and component. The grade scale (`<set>_scale.csv`) runs 0 not about the measure, 1 context only (a hazard, a lesson, a general aim, the World Bank's own screening, an indicator or target, an existing system, another party's work), 2 planned, possible or hedged ("may", "could", "will consider", "where feasible"), 3 a named intervention the project carries out. Grades 2 and 3 count together.
3. **The decision.** The score goes through the measure's probability layer (section 5g) when one is fitted, written as `p_committed_calibrated` (`posterior_probability` in Postgres); the unit counts when it reaches the measure's floor (`floor.<set>`, else `floor.default`): `committed` in `units.csv`, `is_committed` in Postgres. Types, pair checks, package links, reports and views all read this one decision.
4. **The asset** of each unit comes from the asset map (section 5b): the sentence's own (`asset_unit`, level `unit`), else the decayed paragraph sum (`asset_para`, level `paragraph`), else none, as `asset_link`, `asset_link_level`, `asset_link_p`. Nothing is gated on the asset.
5. **Relevance feedback.** After round 0 the query is the centroid of the committed units' vectors minus `feedback.negative_weight` times the centroid of the units that do not count (Rocchio); the corpus is re-ranked by cosine to it and the next `feedback.batch` unseen units are graded, until a round yields fewer committed units than `feedback.min_yield` or `feedback.max_rounds` is reached. The stopping rule is a yield rule for depth, not a recall guarantee; the elusion sheet measures what the pool misses.

Every row carries the wording's firmness (`activity`, `outcome`, `none`, from fixed word lists) and its template wording (`template_projects`: other projects printing the same words; `template_share`: the share of its six-word runs found in two or more other projects): columns to filter on, never cuts.

**Output.** `data/measures/<set>-<version>/units.csv` (one row per unit seen: route, round, rank, cosine, patterns, firmness, template, asset, the prior inputs, the model's raw grade probabilities, the posterior, `committed`, text), a manifest (questions, rounds, models served, calls, cost) and `data/reports/measure_<set>.txt`. The version is a SHA-256 over the search run, the asset map run and the asset layers that apply, the settings (gate, feedback, floor, prior-input version, panel readings), the patterns, the questions and the measure's layer. A re-run of an unchanged measure reads the store and asks nothing. Loaded as `wbg.measure_findings`.

**Cross-measure checks (`src/commit_checks.py`).** Each measure is graded on its own, so once every measure has run, a unit two measures both commit is asked each measure's graded question again, the other measure's boundary beside it (`boundary` column, else its definition). Each side's score goes through that measure's pair layer once fitted (`src/judged.py`) as `p_keep_a` and `p_keep_b`; the views keep the unit in a measure when its side reaches `floor.pair_check` (0.5; `dashboard.apply_measure_pair_checks`). Graded on the workbook's `pair checks` tab. Until 2026-10-22 one choice of four (only A, only B, both, neither).

**Switching a measure off.** A set whose labels are all inactive (green data centres) is not run, and its rows leave Postgres at the next load; its stored answers stay, so switching it back on asks nothing.

## Graded sheets (`src/check_units.py`, `./wbg check <set>`)

A sheet shows the sentence, its paragraph, section, component and the measure's definition, never the model's answer; the person enters a grade, and optionally the asset and type. Rows are drawn by stratum of the current run, and the key file (`data/review/check_units_<set>_s<seed>.key.csv`) records each row's stratum, the stratum's size and the rows drawn, so every figure can be weighted back.

- `--design train` (the default): 30 units whose posterior is within 0.2 of the floor and 10 further away. Its grades fit the probability layer and the skip rule's gate.
- `--design eval`: a random draw by the decision, 60 units that count and 30 that do not. Its weighted figures are the dashboards' precision and recall within the pool; its rows (stratum `eval:*`) never fit a layer or a gate and are never used to edit a definition. Draw it fresh, after tuning.
- `--design bands`, `floor`, `tune`: by band of the posterior, or around each measure's floor; kept for tuning.
- `--elusion`: 25 units just below the pool's gate and 25 far below, never read by the funnel, weighted back to their strata: what the pool missed.
- `./wbg check all --seed <n>` draws every measure with a current run into one workbook (a tab each, plus a package-links tab, section 5e). A seed already drawn is refused.

`--evaluate` stores the grades in `data/labels/<set>_units.csv`, keyed by the text's SHA-256 and the exact question (AGENTS.md rule 9), with stratum and design weight, and writes `data/reports/evaluate_units_<set>.md`: the weighted precision and recall of the decision (posterior at the floor) against the person's grade 2 or more, at several floors and beside the model's score alone, with 95 per cent Wilson intervals on the effective sample size; asset and type agreement; then it fits the layer (reported out of sample, with a suggested floor) and the gate. The headline figures go to `data/labels/measure_quality.csv` (`wbg.measure_quality`), one row per measure, question and kind of sheet. Recall is within the graded pool; the elusion sheet bounds the rest.

**The activities workbook (`src/evaluate_activities.py`, `./wbg evaluate <set> --column <theme>`).** A workbook of activities a person labelled by hand (`data/labels/activities.xlsx`, never in git) is matched to paragraphs by shared eight-word runs, and the report gives, for the activities flagged under a theme, how many have a candidate, a graded unit, a committed unit, and a committed unit with an asset. Labels are per activity and carry no firmness, so this measures whether the funnel finds a commitment somewhere in the activity, not precision.

## 5d. A measure's types (`src/kinds.py`, `./wbg types <set>`)

1. **Propose**, only for a measure with no list a person wrote: the committed units go to a generative model (`anthropic/claude-haiku-5.5`) three times in different seeded orders, every response stored, and the proposals written side by side (`data/types/<set>-<version>/proposals.md`). All twelve measures have a person's list (`analysis/labels/<set>_types.csv`), so this step does nothing for them.
2. **Assign** (`--assign`): each committed unit gets one graded question per type, the form every decision asks, on the types' scale (whether the commitment is of that kind: `kinds.TYPE_SCALE`, or the set's own `<set>_types_scale.csv`); each type's probability goes through the types' layer once fitted (`src/judged.py`), and every type that reaches `floor.types` (0.9 to start: at 0.5 the model gave about four types a sentence) counts, best first (`types.multiple`; the best only when off), so a sentence can sit in two commitments of one measure; a sentence no type reaches has none. Units no approved type counts for (at least `types.gap_min_units`, five) go to the generative model with the existing types, which proposes only new kinds, named `OTH.`, assigned at once by their own graded questions; they show on the dashboards beside the approved types until a person promotes one into the list. Output `data/types/<set>-assign-<version>/assignments.csv` (each type's probability and its phrase match per unit) and `data/reports/types_<set>.txt`.
3. **Merge and rename** are file edits, never a model call: `merge_into` folds a type into another of the same measure, `display_name` changes what is shown while `type_name` stays as asked, so stored answers keep their key; `./wbg publish` applies them.
