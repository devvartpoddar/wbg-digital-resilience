# Checks, Postgres and releases

Part of the method (`docs/methodology.md` is the index). Measured results and trials: `docs/method/history.md`.

## 4. Checks and review

**Automated checks** (`src/audit.py`, `src/audit_procurement.py`) count known defects:
- *Appraisal prose* (narrative and annex): footnote markers glued to words, paragraphs opening as footnote bodies, inline page numbers, runs of spaces and column gutters (both structurally zero since the reader collapses whitespace; kept as a guard on that), tabular rows in prose, paragraphs starting mid-sentence or ending without punctuation, unfolded characters, private-use, replacement and control characters.
- *Procurement*: private-use, replacement and control characters; glued and broken words; second references; mid-word endings; missing or unnormalised references; placeholders; unmapped category, method and status; markers left at the edges; other cells left in a description; component not found; date and amount inconsistencies in the source.

Each check has a gate in the tests, set just above the measured rate, so a regression fails.

**Reading by eye.** A commitment's evidence (`wbg.commitment_evidence`) shows each paragraph with the commitment's sentences marked and a PDF link to the page; any other paragraph is in `wbg.paragraphs_with_document`. The Read and search dashboard and the earlier review spreadsheets were retired on 2026-10-20 and 2026-10-21.

An existing sheet is never overwritten by the pipeline; a new draw takes a new `--seed` (or, by hand, `--force`). A sheet is written aside and renamed, so a half-written one never exists.

**Sensitivity** (`src/sensitivity.py`, `./wbg sensitivity`): how much the cleaned text depends on three settings, written to `data/reports/sensitivity.md`. Nothing the pipeline writes is changed.
- *Paragraph joining*: a sample of 10 documents (PADs and additional financings first, chosen by a hash of their id) is read again from the PDF with the line gap at 1.30 and 1.60 and the loose gap at 2 and 4; the report gives the number of model paragraphs and the share of the default's model text in paragraphs that no longer exist word for word. This re-reads PDFs and is slow on the box.
- *Component tags*: every document is tagged with a tag closing at the section change (the default) and with it running on to the next component heading; the report gives how many model paragraphs are tagged each way and how many differ.
- *Sentences*: every narrative and annex model paragraph is split with the word minimum at 3 (default), 2 and 4, and without the abbreviation list; the report gives the sentence count and how many paragraphs split differently. (The paragraph test counts spans by block, before the five-word and citation-only filters, so its "model paragraphs" are more than `for_model` counts.)

**Postgres** (`src/load_pg.py`, `src/store.py`, `src/schema.py`), database `work`, for querying and for Metabase. The corpus tables are loaded by `load_pg.py` when `./wbg prepare` changed them; the model stages write their own rows as they finish (`store.py`, section 0). Metabase reads the database as a read-only role, shows every table and view, infers types from the Postgres types, follows declared foreign keys from table to table, and imports table and column comments as descriptions; so the loader is where names, types, keys and documentation are decided, and nothing is set by hand on the box.

- *One schema, and only what is read.* `wbg` holds `projects`, `documents`, `paragraphs` (with their text resolved from the offsets), `search_units` (every search unit with its text, lead-in and template score, the parent of every `unit_id`), `components`, `packages`, `notices`, `awards`, `labels` (every label of every set with its definition, which the views join for names), `search_paragraphs` (per label and paragraph, the best search unit), `paragraph_grades` (the asset map: per label and paragraph, the probability of each grade), `measure_findings` (every unit a measure run read: its grade, calibrated probability, asset link, activity kind, actor, conditionality, types; at `feedback_round` 0 it is the candidate pool in reading order) and `sentence_vectors` (the embeddings, `halfvec` with an HNSW index from pgvector 0.7, plain `vector` before). `measure_types` holds each measure's types as shown (merges and display names resolved, section 5d); `label_groups` the assets' reading groups; `measure_finding_lists` unnests the assets, their groups, kinds, actors and types per unit for dashboard filters. Three bookkeeping tables say so in their comment: `loads`, `data_release` and `paragraph_projects` (the paragraph-to-project bridge the views join on). Tables nothing in `sql/views/` or `analysis/sql/` reads are not loaded (sentences, the rejected units, document parts, superseded package versions, the per-unit search scores, the release index): the CSV under `data/` is their record. A load folds an earlier `wbg_internal` schema into `wbg`, carrying its load history over.
- *Names for people.* The CSV files keep their names; `src/schema.py` renames on the way in: full words (`document_id`, `award_id`, `borrower_reference_normalised`), units and currency in the name (`estimated_amount_usd`, `cost_usd_millions`, `word_count`), booleans as `is_`, `in_`, `was_` (`is_for_model`, `in_latest_plan`, `was_sent_to_model`), grades as `most_likely_grade`, `expected_grade`, `probability_grade_0` to `_4`, and the same name on both sides of every join. Pipe-joined lists (`project_ids`, `notice_ids`, `asset_ids_above_threshold`) are arrays.
- *Types.* Every `*_date` column a date, every `*_at` a timestamp, flags boolean, counts integer, amounts and probabilities numeric; a value that does not parse is NULL and counted in the load's output.
- *Keys.* A primary key on every table and a foreign key on every join column, declared `NOT VALID` so an orphan row is reported by the audits rather than failing the load; `components` gets a surrogate `component_id` (document, where it was read, level, number, name key).
- *Comments.* Every table and every column a reader could misread carries a comment written for Metabase: what one row is, where it comes from, the unit.
- *Views as the presentation layer* (`sql/views/`, rebuilt on every load): `packages_with_project`, `latest_plan_packages`, `upcoming_packages`, `notices_with_package`, `awards_with_package`, `paragraphs_with_document`, `paragraph_project_links`, `paragraph_grades_with_text`, `asset_map` (one row per paragraph with the asset the model puts highest), `search_paragraphs_with_text`, `measure_findings_in_context` (a finding with its project, document, component, asset link, kind and text), `candidates_in_reading_order`, `data_as_of`; and the functions `similar_units(unit_id, k)` (nearest units by stored embedding, no outside call) and `search_phrase(phrase, k)` (embeds a new phrase through the box's `openrouter()` function, installed only where it exists). Metabase models and dashboards sit on these, not on the tables; `analysis/sql/` holds the questions, written on the views. The dashboards' own views and functions (commitments, their evidence and packages, the project and measure pages) are in section 5f; `upcoming_packages` is there too, since it now reads the package status.
- A table whose source has not changed is not reloaded; a replaced table takes its keys and dependent views with it, and both are put back at the end of every load. *Atomic loads (2026-10-21):* a full load (`load_pg.py`) and every stage's publish (`store.py`) run in one transaction, views and functions included, so a dashboard sees the database as it was or as it is after the load, never in between; a card that reads a table being replaced waits for the commit, and the load or the publish waits at most two minutes for a lock (`LOCK_TIMEOUT`, `src/load_pg.py`) before it names the sessions holding one (the blocking pids, else every session with an open transaction, with the first 200 characters of its query) and exits non-zero: a load behind a reader must never hang silently (2026-10-20: a Metabase card read `wbg.commitments` for over ten minutes, as a plain view, and every publish waited on its locks; `commitment_units` and `commitments` are materialised since, and a dry run publishes nothing). The run tables (`search_paragraphs`, `paragraph_grades`, `measure_findings`) are replaced set by set, for the sets that have a current run (`load_pg.found_sets`): a set being re-run, or run over another project scope, keeps the rows it had, even when new code changes the table's columns; a set's rows leave only when the set is removed from `inputs/taxonomy/` and `analysis/labels/`. On 20 October four measures (green data centres, network redundancy, renewable energy, resilient infrastructure design) vanished from `measure_findings` between 13:25 and 13:57 because a publish that named no set deleted every row and re-inserted only the sets whose current run it found; that can no longer happen. Tables an earlier layout made under other names in `wbg` are dropped on the first load with the current one.

**Data releases** (`src/release.py`, `./wbg release`, `./wbg status`). A release records which data the store holds and how it was made: the git commit and whether the code or the hand-kept inputs had uncommitted changes, the SHA-256 of the cohort and every taxonomy file, the PDF reader's version, when each project was last fetched, the rows and SHA-256 of every output table, and the search and classification runs present. Its id is a hash of the tables, inputs and runs, so the same data is the same release however often it is cut; a new release keeps a compressed copy of the cleaned tables (about 10 MB) in `data/releases/<id>/`, and `data/releases/index.csv` lists them all. The pipeline cuts one before every Postgres load and after every search or classification run; `wbg.data_release` names the release Postgres holds, so a Metabase card can show "data as of". `./wbg status` says which commit the code is at and whether origin/main is ahead, which release the data is, which stages are out of date with the code, and when each kind of record was last fetched.

**Reports** (`src/run_report.py`): drafts a run note in `data/reports/`, which is copied into the notes vault at `Projects/WBG Digital Resilience/Reports/`. Reports never go into the repository.
