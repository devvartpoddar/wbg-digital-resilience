# Checks, Postgres and releases

Part of the method (`docs/methodology.md` is the index). Measured results and trials: `docs/method/history.md`.

## 4. Checks and review

**Automated checks** (`src/audit.py`, `src/audit_procurement.py`) count known defects:
- *Appraisal prose* (narrative and annex): footnote markers glued to words, paragraphs opening as footnote bodies, inline page numbers, runs of spaces and column gutters (both structurally zero since the reader collapses whitespace; kept as a guard on that), tabular rows in prose, paragraphs starting mid-sentence or ending without punctuation, unfolded characters, private-use, replacement and control characters.
- *Procurement*: private-use, replacement and control characters; glued and broken words; second references; mid-word endings; missing or unnormalised references; placeholders; unmapped category, method and status; markers left at the edges; other cells left in a description; component not found; date and amount inconsistencies in the source.

Each check has a gate in the tests, set just above the measured rate, so a regression fails.

**Reading by eye.** A commitment's evidence (`wbg.commitment_evidence`) shows each paragraph with the commitment's sentences marked and a PDF link to the page; any other paragraph is in `wbg.paragraphs_with_document`.

An existing sheet is never overwritten by the pipeline; a new draw takes a new `--seed` (or, by hand, `--force`). A sheet is written aside and renamed, so a half-written one never exists.

**Sensitivity** (`src/sensitivity.py`, `./wbg sensitivity`): how much the cleaned text depends on three settings, written to `data/reports/sensitivity.md`. Nothing the pipeline writes is changed.
- *Paragraph joining*: a sample of 10 documents (PADs and additional financings first, chosen by a hash of their id) is read again from the PDF with the line gap at 1.30 and 1.60 and the loose gap at 2 and 4; the report gives the number of model paragraphs and the share of the default's model text in paragraphs that no longer exist word for word. This re-reads PDFs and is slow on the box.
- *Component tags*: every document is tagged with a tag closing at the section change (the default) and with it running on to the next component heading; the report gives how many model paragraphs are tagged each way and how many differ.
- *Sentences*: every narrative and annex model paragraph is split with the word minimum at 3 (default), 2 and 4, and without the abbreviation list; the report gives the sentence count and how many paragraphs split differently. (The paragraph test counts spans by block, before the five-word and citation-only filters, so its "model paragraphs" are more than `for_model` counts.)

**Postgres** (`src/load_pg.py`, `src/store.py`, `src/schema.py`), schema `wbg` in database `work`, for querying and for Metabase. `./wbg prepare` loads the corpus tables when they changed; each model stage writes its own rows as it finishes (`store.py`); `./wbg publish` catches up. Metabase reads the schema as a read-only role and imports table and column comments, so the loader decides names, types, keys and documentation, and nothing is set by hand on the box.

- *Corpus*: `projects`, `documents`, `paragraphs` (text resolved from offsets), `components`, `search_units` (every search unit with its text, lead-in and template score), `packages`, `notices`, `awards`, `labels` and the copies of each set's phrases, patterns and scale, `measure_types`, `sentence_vectors` (`halfvec` with an HNSW index where pgvector 0.7 is installed). Bookkeeping, said so in their comment: `loads`, `data_release`, `paragraph_projects`.
- *The model runs, current run of each set*: `search_paragraphs`; `paragraph_grades` (the asset map: one row per sentence and asset, each grade's probability and `posterior_probability`); `unit_assets` (each sentence's asset as the pipeline decides it, section 5b); `measure_findings` (every unit a measure read: route, round, asset link, the model's grade probabilities, `posterior_probability`, `is_committed`, type); `unit_pair_checks`; `unit_paragraph_context`; `package_assets`; `commitment_packages`.
- *The record of judgement*, so evaluation is reproducible from SQL: `graded_labels` and `graded_package_links` (every grade a person gave, keyed by text and question, with stratum and design weight); `check_draws` (every row ever drawn for grading, with its stratum's size); `posterior_layers` and `skip_gates` (what was fitted, on which question); `runs` (every model run's manifest, as JSONB: questions, settings, models served, cost; unlike the run tables, every run written); `spend` (the ledger); `answers` (the answer store: every stored answer under its key, as JSONB; the state's text is not repeated); `measure_quality` (each evaluation's headline figures, by measure, question and kind of sheet).
- *Names for people.* `src/schema.py` renames on the way in: full words (`document_id`, `borrower_reference_normalised`), units in the name (`estimated_amount_usd`, `word_count`), booleans as `is_`, `in_`, `was_`, the grade probabilities as `probability_grade_0` to `_3`, the decision's probability as `posterior_probability`, the same name on both sides of every join. Pipe-joined lists are arrays; `*_date` columns are dates, `*_at` timestamps, a value that does not parse is NULL and counted.
- *Keys and comments.* A primary key on every table and a foreign key on every join column, declared `NOT VALID` so an orphan row is reported by the audits rather than failing the load; a comment on every table and every column a reader could misread.
- *Views* (`sql/views/`, rebuilt on every load) are the presentation layer: the corpus views (`packages_with_project`, `latest_plan_packages`, `notices_with_package`, `awards_with_package`, `paragraphs_with_document`, `paragraph_project_links`, `paragraph_grades_with_text`, `asset_map`, `search_paragraphs_with_text`, `measure_findings_in_context`, `data_as_of`), the functions `similar_units(unit_id, k)` and `search_phrase(phrase, k)` (the latter only where the box's `openrouter()` function exists), and the dashboards' views (section 5f). `analysis/sql/` holds questions written on the views.
- *Loads.* A table whose source key has not changed is not reloaded. A full load and every publish run in one transaction, views included, so a card sees the database as it was or as it is after; a load waits at most two minutes for a lock (`LOCK_TIMEOUT`), then names the sessions holding one and exits non-zero. The run tables are replaced set by set, for the sets with a current run (`load_pg.found_sets`), so a set being re-run keeps its rows; a set's rows leave only when the set is removed. A run over named projects is not published (`$WBG_PUBLISH_SCOPED=1` publishes it, for a database that holds only those projects). Tables and columns an earlier layout made (among them `unit_scope` and the second-pass columns, dropped on 2026-10-22) are dropped by the first load with the current one.

**Data releases** (`src/release.py`, `./wbg release`, `./wbg status`). A release records which data the store holds and how it was made: the git commit and whether the code or the hand-kept inputs had uncommitted changes, the SHA-256 of the cohort and every taxonomy file, the PDF reader's version, when each project was last fetched, the rows and SHA-256 of every output table, and the search and classification runs present. Its id is a hash of the tables, inputs and runs, so the same data is the same release however often it is cut; a new release keeps a compressed copy of the cleaned tables (about 10 MB) in `data/releases/<id>/`, and `data/releases/index.csv` lists them all. The pipeline cuts one before every Postgres load and after every search or classification run; `wbg.data_release` names the release Postgres holds, so a Metabase card can show "data as of". `./wbg status` says which commit the code is at and whether origin/main is ahead, which release the data is, which stages are out of date with the code, and when each kind of record was last fetched.

**Reports** (`src/run_report.py`): drafts a run note in `data/reports/`, which is copied into the notes vault at `Projects/WBG Digital Resilience/Reports/`. Reports never go into the repository.
