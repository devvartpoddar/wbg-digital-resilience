# 5g. One decision system for every question to the decision model

Part of the method (`docs/methodology.md` is the index). Measured results and trials: `docs/method/history.md`.

Every question the pipeline puts to the decision model (TypeSafe's Jev, pinned to the snapshot in `questions.MODEL`, through OpenRouter's decisions endpoint) is handled the same way; only the thresholds differ, and each is one line of `inputs/config/control_panel.csv` (`src/wbg_portfolio/panel.py`; a line the code needs and the panel lacks is an error, never a default).

## The asker (`src/wbg_portfolio/ask.py`, `src/wbg_portfolio/questions.py`, `src/wbg_portfolio/api.py`)

Two forms of question. A classification (an asset, a measure) asks `questions.graded_question`: how the sentence relates to the label, on the shared 0-3 scale (`analysis/labels/scale.csv`: 0 not described, 1 background or another party's work, 2 the project may deliver it, 3 the project explicitly finances, delivers or requires it). Its score is the probability of the grades the panel counts (`read.grades`, 2 and 3), out of the total. A check made after a classification (a type, a package to an asset, a package to a measure) asks `questions.fit_question`: does the label apply, yes, unsure or no, told what is already decided; its score is P(yes). Both read the raw probabilities (`questions.score`), never a rounded column.

Every sentence-level question sends the same state (`questions.Corpus.state`): the sentence with its list lead-in, the section title and the component heading, and with `ask.context` = `paragraph` the paragraph too. A package sends its description and plan component.

`ask.ask` takes items (an id, a state, the questions for it), reads the store (`<store>.answers`, `$WBG_STORE`, default `<schema>_store`; keyed on model, state and question), reads the old file store once for anything it holds and copies it in, and asks the rest in batches (`ask.batch_items` items sharing a question set, up to `ask.batch_max_chars` characters, ordered by the hash of their state so which items share a request depends on the items alone; one item a request when `ask.batch_items` is 0). Every answer is stored under its own item and question, with the snapshot that served it and its share of the call's cost. An incomplete answer is a failed request; a run with failed requests writes nothing and resumes next time; a refusal (bad key, no credit) stops at once. Spend is recorded per step in `<store>.spend`: the step's row is written at its first request and brought up to date at every request, so a kill loses at most the request in flight; `--max-spend` is enforced from that ledger (`api.Spend`, `running.md` "Spend").

## The funnel (`src/wbg_portfolio/funnel.py`), the same for assets and measures

1. **Round 0.** A label's question goes to every sentence in scope that a word pattern of the label matches (`<set>_patterns.csv`), every sentence whose best cosine over the label's phrases and definition reaches the label's gate (the skip rule's fitted gate, else `measure.gate_cosine` or `asset.gate_cosine`; 0 asks every sentence), and every sentence the store already answers under the current question (nothing paid for is dropped). `measure.top` adds the best N by cosine (off).
2. **Rounds** (`src/wbg_portfolio/feedback.py`): the sentences that count at the ask floor (`floor.ask`, `asset.ask_floor`: what a round counts as a yes, not what is decided) are averaged, minus `feedback.negative_weight` times the sentences asked that do not (Rocchio, no query term); the corpus is ranked against that query and the next `feedback.batch` unasked sentences are asked; a label stops when a round yields fewer than `feedback.min_yield` or after `feedback.max_rounds` (`asset_feedback.max_rounds` for the asset map; 0 turns rounds off). A yield rule for depth, not a recall guarantee; the elusion draw looks below the gate. Rounds run only when round 0 asked something new of a set already scored: re-seeding them from a larger stored pool would otherwise move the admitted set between runs that changed nothing else. A set whose questions, gates, patterns, search run and settings match its last finished run is skipped whole (`wbg.funnel_state`). Before each feedback round is asked, what it picked (and whether the rounds run at all) is committed to `wbg.funnel_rounds` under the run's fingerprint and selection; a run of the same set stopped before it wrote its scores replays the same rounds from it when started again (the answers come from the store), so it asks and writes what the uninterrupted run would have, rather than taking a stopped round's answers into round 0. The record is removed when the scores are written.
3. **Scores.** Every answer is one row of `wbg.scores`: kind (asset, measure), label set, label, unit, the score, the raw answer, the snapshot served, the route it was first asked by (embedding, pattern, both, stored, feedback), its round and its cosine.

## The decision (`src/wbg_portfolio/decide.py`)

`./wbg_portfolio publish` reads every kind's scores once, through the label's probability layer when one is fitted and `posterior.on` is true (else the score stands), against the label's threshold, and writes the tables the views read: `measure_findings` (`is_committed` by the band rule; `score_first`, `score_context`, `second_grade`, `decided_by`, `is_digital`, `digital_p`, `instrument`; the unit's assets; its types at `floor.types`, every one with `types.multiple`), `paragraph_grades` and `unit_assets` (a sentence's own assets at `asset.floor`, else with `asset.decay` on the assets whose decayed sum over the earlier sentences of its paragraph reaches `asset.paragraph_floor`, every one with `asset.multiple` else the best), `package_assets` (a package has an asset at `link.asset_yes`, or from `link.asset_band_low` when the chat model's second look says yes), `commitment_package_links` (section 5e: strong at `link.strong_yes`, or by a shared asset), `activities`. The views join and aggregate; `commitment_units` (section 5f) is the one place that adds the dashboards' own filters. Every comparison is "at or above".

| Decision | Gate | Floor |
|---|---|---|
| Asset map | fitted gate, else `asset.gate_cosine`; patterns; rounds | `asset.floor`; `asset.decay`, `asset.paragraph_floor`, `asset.multiple` |
| Measure | fitted gate, else `measure.gate_cosine`; patterns; rounds | the band rule (`band.*`) |
| Measure second look | a first score in `[band.ask_low, band.ask_high)` and a digital P(yes) of `digital.ask_low` or more | `band.low`, `band.keep`, `band.context`, `band.second_grade` |
| Digital | every sentence with a first-pass score in the asked band (asked before the measure second looks) | `digital.floor`; what is asked: `digital.ask_low` |
| Type | every committed, digital unit | `floor.types`, `types.multiple` |
| Package to asset | `link.asset_top` by cosine | `link.asset_yes`, `link.asset_band_low` |
| Package to measure (strong link) | every package that has an asset, for each measure of its project | `link.strong_yes` |

## The band rule, the digital rule and the second look (`src/wbg_portfolio/second.py`, `src/wbg_portfolio/chat.py`)

The pattern for every step from 2026-11-20: **the judge decides; anything in the uncertain band gets the same second look; both must agree.** The judge is the decision model above. The second look is one pinned chat model (`second.model`, asked through `/v1/chat/completions`, temperature 0, one item a request, told to reply with a short JSON object). `src/wbg_portfolio/chat.py` stores its answers in the same table as the decision model's (`<store>.answers`: model, state, question), counts requests and `--max-spend` in the same ledger, and reads a reply strictly: anything but exactly the JSON asked for is never stored in `answers` (which is only added to, never updated or deleted); each failed attempt is one row of `<store>.chat_failures` (model, state, question, the reply's text, time). A question that failed `second.max_attempts` times (2) is not asked again and is counted in the log as "gave up"; it is never read as a yes. Every request carries `max_tokens` (`second.max_tokens`, `activities.max_tokens`); the estimate before a step is the prompt's length at `second.price_in_per_mtok` plus the largest reply at `second.price_out_per_mtok` (an upper bound), and a response that reports no `usage.cost` is priced from its token counts at the same prices (or from the estimate), so the cap cannot be bypassed by a missing field.

**The band rule** (`decide.band_rule`) is the one place that says a sentence commits a measure:

- a first-pass posterior of `band.keep` (0.90) or more is committed on its own (`decided_by` = score);
- from `band.low` (0.50) up to `band.keep` it is committed only when two second looks agree: the decision model asked the measure's graded question again with the paragraph beside the sentence (kind `measure_ctx`, P(grades 2, 3), at least `band.context` 0.70) and the chat model grades the pair at least `band.second_grade` 2 on the same 0-3 scale (kind `measure_second`; shown the sentence with lead-in, section and component, no paragraph). `decided_by` = second_look;
- a pair in the band whose second look is missing is not committed; the publish log counts it as "waiting for a second look";
- below `band.low` it is not committed.

The context question is the same question with one sentence in front saying that only the sentence in the `sentence` field is judged and the `context` field is the paragraph around it, for reference (`questions.in_context`; `Corpus.context_state` cuts the paragraph to `second.context_chars`). The first-pass state and every stored first-pass answer are unchanged. The later stages (types, policy, assets' second look, links) ask about the sentences committed under the band rule and digital.

**The digital question** (kind `digital`) is asked once per sentence in the asked band of any measure, whatever its measure, and before the measure second looks: the fit question "does a digital asset or the digital sector apply", defined by the `digital` row of `inputs/taxonomy/flags.csv`, with the paragraph beside the sentence. A sentence is digital at P(yes) of `digital.floor` (0.50) or more. A committed sentence counts on the dashboards' commitment views only when it is digital (`measure_findings.is_digital`, `digital_p`); the committed sentences that are not stay in `measure_findings` and are listed in the view `not_digital_findings`. The rule is the same for every family and measure. **It also decides who is asked the measure second looks** (what is asked and what decides, again): the context question and the chat grade are asked only for sentences whose digital P(yes) is `digital.ask_low` (0.20) or more, because a sentence that is not digital is published nowhere and a second look for it would be paid for and thrown away. `digital.floor` (0.50) decides; `digital.ask_low` leaves room to lower the floor later without a top-up, and the load fails when `digital.ask_low` is above `digital.floor`. A sentence with no digital answer yet is waiting for it, not left out: the stage prints how many of each, and a dry run says it cannot estimate the second looks until the digital question has run. A pair left out as not digital is not reported as waiting for a second look.

**The policy flag** (kind `policy`) is the chat model's reading, for each committed sentence the digital question says is digital (the types and links are asked about the same set), of investment or policy instrument (the `policy` row of `flags.csv`), shown the paragraph; published as `measure_findings.instrument`. Nothing moves a sentence between measures on it.

**What is asked and what decides (2026-11-20).** Each second look has two sets of lines in the panel, and they are kept apart: which pairs are asked (`band.ask_low` 0.5 and `band.ask_high` 1.01 for the measures; `link.asset_ask_low` 0.3 and `link.asset_ask_high` 1.01 for a package's assets; `asset.ask_high` 1.01 for the assets of a sentence, where 1.01 means every committed, digital sentence) and which pairs count (`band.low`, `band.keep`, `link.asset_band_low`, `link.asset_yes`, `asset.floor`, read at publish). A look stored for a pair at or above `band.keep` changes nothing in its decision; it is published in `score_context` and `second_grade` so it can be read. Because the asked range is wide and the decision is read at publish, any decision threshold can be moved in either direction inside the asked range and re-published with no model call; only a move outside it asks again. Load fails with a plain message when a decision band is wider than its asked band (`band.ask_low` above `band.low`, `band.ask_high` below `band.keep`, the same for the `link.asset_` pair, `asset.ask_high` below `asset.floor`), because pairs in the gap would wait for ever. Nothing under 0.50 is asked (a trial found none right in 40). The first-pass asset still wins at `asset.floor`; the chat model's asset, where the first pass also has one, is published in `unit_assets.second_look_asset_id` so the agreement of the two can be measured. The digital question, the policy flag and the package-to-measure question store a score for every item they are asked about and skip none by a threshold of their own, so `digital.floor` and `link.strong_yes` are tunable at publish. What they are asked about differs. The digital question is asked for every sentence with a first-pass score in the asked band `[band.ask_low, band.ask_high)` for at least one measure, not only the committed ones, because it decides whether a sentence counts and so must not block free tuning (and it is asked before the measure second looks, which it gates); the decision is unchanged: only committed sentences are published as digital or not, and a committed sentence with no digital score is waiting, never a yes. The policy flag, the asset second look and the types are asked for committed, digital sentences only (and the package question for the packages that have an asset): they label a sentence, they do not decide whether it counts. So loosening a threshold (`band.keep`, `band.low`, `band.context`, `band.second_grade`, `link.asset_yes`, `asset.floor`) publishes at once with the newly kept sentences counted, and their policy flag, second-look asset and types are filled at the next run, from the stored answers for the rest.

**Evidence (2026-11-20; every figure graded by models, not by people; the trials are in `history.md`).** Kept sentence x measure pairs scoring 0.90 or more are 96 per cent right; those at 0.80 to 0.90, 76 to 82 per cent. On a held-out sample of 360 pairs the band rule moved precision from 0.92 to 0.96 and recall from 0.41 to 0.61 (three-grader majority), and from 0.86 to 0.92 and 0.48 to 0.74 under the strictest grader; the thresholds were chosen on the same 360 items, so these figures are optimistic. "Is this digital" with the paragraph as context: 96 per cent precision and 90 per cent recall on "not digital", 2 to 3 per cent of truly digital sentences wrongly excluded (asked on the sentence alone, 10 to 12 per cent). A stored score is one noisy draw: two batches of 50 agree at 0.96 for measures.

## The probability layer (`src/wbg_portfolio/posterior.py`) and the skip rule (`src/wbg_portfolio/skip.py`)

The layer is a logistic regression stacked on the logit of the model's score, a vote of the sentences a person graded for the label (each weighted by exp(`posterior.sharpness` x (similarity - 1))) and the difference between the sentence's similarity to the graded-yes centroid and to the graded-no centroid (`posterior.centroid`). A graded sentence never votes for itself. `posterior.pool` fits each decision kind's labels together, one intercept per label and shared slopes, under a ridge prior (`posterior.ridge`); a label needs `posterior.min_each` graded yes and no, the pool `posterior.min_graded` rows. The fit weights each graded row by its design weight raised to `posterior.fit_weight_power` (0: every row once); the reports always use the full design weight. It is checked out of fold by project (`posterior.folds`), whether or not `posterior.on` is true, so the evaluation can always say whether the layer beats the raw score. Each layer is keyed on the exact question its label asks and stored in `wbg_store.fits`.

The skip rule: a label's gate is the highest cosine that leaves at most `skip.max_loss` of the graded yes (training rows, at their design weights) below it, a yes a pattern matches never counting against it; fitted from `skip.min_positives` yes or more, keyed on the question and the search run whose cosines it read. The report gives the 95 per cent upper bound on the loss (about 3/n with n yes and none lost). Sentences a grader named on the closing task as committing a measure the funnel never asked count as graded yes below the gate.

## Grading and evaluation (`src/wbg_portfolio/grading.py`)

**Tasks.** `./wbg_portfolio check draw --seed n --design train|eval|elusion` draws items by stratum (training: 30 sentences a measure within 0.2 of `floor.default` and 10 further, 15 and 5 an asset, 60 sentences whose asset comes from their paragraph, 15 package assets a band, 50 random sentences; evaluation: 900 committed sentences over the measures and 30 not committed a measure, 20 and 5 an asset; elusion: 25 sentences a measure just below its gate and 25 far below) with Poisson sampling on one uniform per item (a hash of the seed and the item, so a draw is repeatable), each line shown with exactly its own chance, the assets of a shown commitment drawn with its measure line. It writes one JSONL task per decision: the sentence (or package), its paragraph with the sentence marked, project, section, component, the label's name and definition, the exact question the model was asked, the scale, the allowed values, the design weight, and for a type its parent measure task. A block's last task asks which other listed ids apply (`none` or ids joined by `|`).

**Fills.** The grader writes `{"task_id", "grade", "rationale"}` per task. `./wbg_portfolio check fill --seed n --file <jsonl> --grader <who>` refuses the whole file when any task is unanswered, any answer is off its list or any id is unknown, then stores the grades in `wbg_store.grades`, keyed on the kind, the label and the item's text (a package: its description's checksum), with the design, the grader, the rationale, the stratum, the weight and the question hash as provenance. A later grade of the same item under the same label and design replaces an earlier one.  A type counts only under a measure graded 2 or more; `unsure` leaves a task out. A wording edit keeps the grades: the item and the label are the key, the question is the record.

**Evaluation.** `./wbg_portfolio check evaluate` matches every grade of every kind to the current scores by the item's text, and for each kind reports weighted precision and recall at a range of floors with 95 per cent Wilson intervals on Kish's effective sample size, the layer's out-of-fold figures beside the raw score's, weighted AUC, the suggested floor (the most recall at `floor.target_precision`, on a 0.01 grid), and for measures and assets the fitted gates. Training rows fit; evaluation rows never do, and only their figures are quoted (a floor read off the rows it is measured on is an upper estimate). `--grid` also ranks the layer settings out of fold (slow; off by default). Output: `data/reports/evaluate.md`, `wbg.measure_quality`, the fits.

**The evaluation sample** (`./wbg_portfolio check sample|grade|tune`) is separate from these sheets: a Poisson draw from what is published, graded by three models, tuned on its tuning set and reported on its holdout set; its holdout figures are `measure_quality` rows with sheet `holdout`, which the evaluation above keeps when it rewrites its own sheets (`docs/method/evaluation.md`).

The evidence behind each panel value, with the figures it was tuned on, is in `docs/method/history.md` ("Why each control panel value is what it is").
